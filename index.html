1 · The big picture

We have entered the era where software improves itself. This is what that looks like for BREEAM review.

Traditional software is finished the day it ships, and ages from that moment. This system is the opposite: it is an agentic micro-engine — a growing body of firm-owned knowledge (calibrated rules, reviewer verdicts, regulation packs, coverage ledgers) that every review adds to, and that AI agents read, apply, and extend. The software your team uses next quarter will be measurably better than today's — not because a vendor shipped an update, but because your own reviewed reports taught it. Improvement is the product's default state; humans approve every step of it.

The concrete problem it solves today: Sureal reviews BREEAM credit reports with a four-pairs-of-eyes principle — every draft is read, in full, by multiple senior reviewers before it reaches a client. That produces excellent reviews, and consumes senior hours on every report, on checks that repeat from document to document: terminology, consistency, completeness, the firm's hard-won rules about what assessors accept.

This system captures those repeating checks — distilled from hundreds of historical reviewer comments into a calibrated, firm-owned rulebook — and applies all of them, every time, provably, in about five minutes, writing its findings as ordinary Word comments into the document itself. The senior eyes then do what only senior eyes can: judge, decide, and sign.

The product is not any single credit review. The product is the infrastructure plus the rulebook — a system Sureal's team extends themselves (new credits, new rules, new schemes) and that compounds: every reviewed report can teach the next one.

2 · The current solution — and why it's the right one

A reviewed document goes through a pipeline of thirteen steps. The principle: deterministic code where determinism belongs, AI where judgment belongs, and a ledger proving nothing was skipped.

Extracttext, tables, figuresCODE
Mechanical checksformatting · names · scheme matchCODE
Audit wavenumbers · quality · visuals · annexes — in parallelAI
Rule sweepevery calibrated rule: finding or checked-cleanAI
Consolidatemerge · dedupe · prioritiseAI
Word commentsanchored in the documentCODE
Verify + ledgercoverage proven per ruleCODE

The step that matters most is the rule sweep: the system must return a verdict on every rule in the firm's rulebook — a finding anchored to the exact sentence, or an explicit "checked, clean" with a reason. The count is enforced by code. Coverage is not hoped for; it is a file (rule_coverage.json) delivered next to every review.

Why not just paste the report into a chatbot?

Because a chat gives you a sample; this gives you a guarantee. Five differences, each testable: (1) a chat produces different findings every run — this checks all rules, every run, provably. (2) A chat knows BREEAM; it doesn't know Sureal — the rulebook is the firm's own judgment, found in no model's training data. When we measured it, a generic review deployed zero of the firm's calibrated rules; this system deploys all of them. (3) A chat outputs text to copy-paste; this writes anchored Word comments into the client's own file. (4) A chat forgets each session; here, every reviewer reply becomes candidate training for next month's rulebook. (5) A chat changes behaviour silently when the vendor updates; this system is versioned — behaviour changes arrive as deliberate, tested releases you can diff. Full measured evidence: Addendum A.

3 · How to install

You need: a Windows 10/11 PC, the install-win.ps1 file Sureal sent you (it is personal to your organisation — don't forward it), and the API key Sureal provides. No administrator rights are needed, and nothing is installed system-wide — everything lands under your own user profile.

  1. Save install-win.ps1 to your Downloads folder.
  2. Open PowerShell (the normal one, not "as administrator"), and paste: cd $HOME\Downloads; powershell -ExecutionPolicy Bypass -File .\install-win.ps1
  3. Follow the prompts. The installer finds your Python (or tells you exactly how to get it, no admin needed), fetches the software, asks once for the API key, runs a full offline self-test, and opens the app in your browser.
  4. Bookmark http://127.0.0.1:8000 — that's the app. It runs entirely on your own machine; documents never leave it except for the AI review calls.

If the install stops on a network or certificate error. Some corporate networks block the Python package index outright, and no certificate change fixes that. Ask Sureal for wheels-win64.zip, unzip it so the folder wheels-win64 sits next to install-win.ps1, and run the installer again — it will then install with no network at all.

If the install stops saying a package does not support your Python version. That one is on us, not on you or your IT team. Send Sureal the line the installer prints; the fix is one line on our side and then you re-run the installer.

Advanced / older installs only: if your machine was set up through WSL rather than natively, the equivalent scripts are install.ps1, scripts/launch.sh and scripts/update.sh (add --check-only to preview an update), run inside wsl -d <distro> — your own distro name, which wsl -l -q lists. New installs do not use WSL.

Starting it again later

Use the Sureal Report Reviewer desktop icon the installer created. If it is ever missing, this is the same thing: powershell -ExecutionPolicy Bypass -File "$env:LOCALAPPDATA\Sureal\breeam-pipeline\scripts\launch-win.ps1" -Open

Updating

When a new version exists, a banner appears in the app: "Version X available." Open the Update page and press the button, or paste the single line it shows into PowerShell: powershell -ExecutionPolicy Bypass -File "$env:LOCALAPPDATA\Sureal\breeam-pipeline\scripts\update-win.ps1"

To see what an update would do without applying it, add -CheckOnly to that line. The updater is transactional: it checks nothing is running, backs everything up, applies the update, re-runs the full self-test, and rolls back automatically if anything fails. Your local data — your rules, your reviews — is never touched.

4 · How to generate a review

  1. Open the app → Upload. Choose the report (.docx), select the scheme (NC2016 / RFO2015 / V6 / V7), the credit, the stage, and confirm the building name.
  2. Wait ≈ 5 minutes. The status page shows each phase as it completes.
  3. Download. The file keeps its original name — save it over your working copy or alongside it.
  4. Open it in Word. The review is there as ordinary comments, each anchored to the exact sentence it concerns. Every comment opens with the action — see "Reading a comment" below.
  5. Reply in Word to any comment you disagree with — a short "disagree, this is present in annex 3" or "stop flagging this" is enough. This is not politeness; it is how the system learns (§6). Agreeing silently is fine; disagreeing silently wastes the signal.

Reading a comment

Every comment has the same four parts, in the same order, so you can triage a whole document by reading first lines only and then going back for the ones that matter.

Add the calculator version to the Table 3 caption          ① the action
BREEAM requires the tool version so the calculation
can be reproduced.                                          ② why it matters

Proposed caption: "Table 3 — Mat 06 calculator v2.1 output"  ③ detail (often absent)

— HIGH · Source: MAT06.CD.03 · Annex A, p.12                ④ the footer
① The actionAn instruction, never a label — "State the calculator version", not "Missing calculator version". Twelve words at most. This line alone should be enough to decide whether the comment needs your attention now, later, or not at all.
② Why it mattersOne sentence: the requirement, the risk, or the inconsistency behind the action.
③ The detailPresent only when it adds something the first two lines do not — proposed wording, an evidence reference, or the other places the same issue appears (as one line beginning Also:). Most MEDIUM and LOW comments stop after line 2; CRITICAL and HIGH ones may run longer when there is genuinely more to say.
④ The footerSeverity, the rule IDs that fired, and where in the document. The Source: IDs are how a reply you write gets traced back to the rule that produced the comment (§6) — so keep them in the thread when you reply.

Comments were previously several times this length, repeating the action as a title, again under "Action Required", and a third time as proposed text. If you still see one shaped that way, it came from an older version — the version is stamped at the foot of every page of this manual.

The coverage ledger. Next to each review the system writes rule_coverage.json: which rules produced findings, which were checked and found clean. Nothing is sampled; everything is swept. You can show this file to a client or an assessor as evidence of review rigour.

If the document states a different BREEAM version than the scheme you selected, the review will flag it (SCH.1). That flag is usually right — check the project's actual registration before dismissing it.

5 · How to improve a credit module

Each credit (Mat 06, Tra 05, …) has its own rule pack. Packs start as scaffolds — the pipeline runs, mechanical checks work, but the credit-specific rulebook is empty. A pack becomes calibrated by learning from history:

What you feed itMinimum for a calibrated pack
Fully reviewed historical reports (.docx with the reviewers' comments still in them), same credit & stage8–10 documents. The Mat 06 concept-design pack — the reference standard — was calibrated on 8. Below that, the pack still works but is flagged low-confidence and its findings deserve extra scepticism.
Comment densityA useful document carries ≥ 6 substantive reviewer comments. Cover pages and sign-offs teach nothing.
  1. Collect the reviewed DOCX files. Do not rename anything to *_ORIGINAL.docx — that suffix is reserved by the system.
  2. App → Expert Rules → select the credit and stage → upload the documents.
  3. The system extracts every reviewer comment, clusters recurring concerns into candidate rules, and applies safety gates: a candidate needs a correct and an incorrect example, and must appear in at least two documents. Singletons are parked, not published.
  4. Candidates go to a staging file — never directly into the live rulebook. The result page shows a green button: Download candidates file — send to Sureal. Do that. Nothing takes effect until a human at Sureal has approved each rule individually.
  5. Approved rules arrive in a future update, and from then on every review of that credit applies them — with the coverage ledger proving it.

6 · The monthly calibration

Once a month, the system learns from the month's real work. Two signals feed it: the replies reviewers wrote on AI comments (§4 step 5), and new reviewed documents (§5). The routine:

  1. Reviewers: upload the month's commented reports via Expert Rules whenever convenient — end of month at the latest. Download each candidates file and send it to Sureal. That attachment is the entire hand-over; nothing moves automatically.
  2. Sureal: reviews every candidate and every disagreement verdict in an interactive approve/reject session, rule by rule. Accepted changes are validated, version-stamped, and released.
  3. Everyone: runs the update when the banner appears. The improved rulebook is now live for the whole team at once.

⚠ Pitfalls — each of these was learned the hard way

  • Never edit the rule database files by hand. A hand-calibrated ruleset was once overwritten by a well-intentioned bulk operation and survived only because of version control. All changes go through the staged approve flow, which validates before every write.
  • Keep working in the reviewed file. Your replies to the AI's comments are only visible to the system in the file that contains them. If you copy text into a fresh document, the learning signal dies with the old file.
  • One report, one upload per round. Uploading the same document twice inflates rule frequencies and can push weak rules over the acceptance threshold.
  • Resolve scheme flags, don't dismiss them. When the system raises SCH.1 (document says V6, review ran NC2016), confirm the project's actual registration first. This mismatch was found on multiple historical documents — it is not a false alarm by default.
  • The candidates file does nothing on your machine. Until it is sent to Sureal and approved, it's a proposal in a folder. Send it.
  • Disagreement is data. The most valuable thing a reviewer can do for the system is reply "disagree — here's why" on a wrong comment. Suppressed annoyance teaches nothing; a two-line reply retrains the rulebook.

8 · This is a V1 — where it goes from here

What you are using today is the first rung of a ladder. The destination is not "AI instead of experts" — it is a steadily rising division of labour in which the human never leaves the loop; the loop moves up.

V1 — the tireless junior you are here
The system drafts the review; every calibrated rule is swept and proven. Experts still author the final judgment. Value: senior hours stop being spent on mechanical and rulebook checks. Reviewer time ≈ −40 %.
V2 — the reliable colleague
Months of reply-verdicts and monthly calibration have tuned the rulebook to the team. Drafts need visibly less correction; the coverage ledger ships with every client review as a rigour statement. Requires: sustained §6 discipline. Reviewer time ≈ −60 %.
V3 — validation-ready
The report review arrives practically flawless in Sureal's own voice — house terminology, house structure, house judgment — because the style itself is learned from accumulated verdicts. The expert's role shifts from author to approver: read, decide, sign. Requires: the v1.3 evaluation harness proving per-rule precision, so "practically flawless" is a measured claim, not a feeling. Reviewer time ≈ −80 %.
V4 — the standard
New staff are trained by the system's rulebook rather than the reverse. The firm's expertise is an institutional asset — versioned, auditable, teachable — not tacit knowledge in a few senior heads.

Each rung is earned by data, not declared by software: V2 by calibration months, V3 by measured precision. The calculator above has a stage toggle — the business case for climbing is yours to inspect.

Beyond the ladder — the iteration engine

The ladder describes the review getting better. The bigger opportunity is the rest of the value chain. Look at the life of a credit report today:

Project datagatheringHUMAN
Evidence & figuresmaps · screenshots · annotationsHUMAN
Authoringsomeone types every reportHUMAN
Reviewthis systemAUTOMATED ✓
Correctionreviewer + AI commentsHUMAN + AI
Validation & deliverysign and sendHUMAN

Only one step is automated so far. Every [HUMAN] box is a candidate for the same treatment — and because the system's knowledge lives in a repository agents can read, the system can propose these expansions itself. A concrete example: for transport credits (Tra 01/02), a person today takes Google Maps screenshots and hand-annotates transit stops, walking distances and amenities. An agent that has read this project can notice that, propose it, and build a prototype that generates those figures from a project address — evaluated against the figures in historical reports, approved by a human, and only then added to the pipeline. Analyse → propose → prototype → measure → approve → graduate: the same gated loop that governs the rulebook, applied to the software's own scope.

That is the story this project tells: not a tool that was built once, but a system that keeps finding its own next improvement — with Sureal's experts holding the approval pen at every step.
