1 · Quickstart — your two jobs

You do two things with this app. Everything else in this manual is background.

Job 1 · every report

Get a review

Upload a report; it comes back with AI comments anchored in the document, ready to work through in Word.

~2 min of your time · 5–20 min for the system Job 2 · once a month

Teach the AI

Reply in Word to comments you disagree with, then drop the finished file into the shared folder. That's the entire hand-over.

~2 min per document · monthly

Run a report — five steps

  1. Open the app via the Sureal Report Reviewer icon on your desktop. It starts the app if needed and opens it in your browser. You're in when the green Sureal Report Reviewer page loads.
  2. Check the Catalogue — the Catalogue page in the app shows every credit and how far along it is. This manual deliberately never lists them: the list grows every month, and the Catalogue is always current. Three levels:

    Calibrated — the full review, including Sureal's own expert rules. Treat it like a careful junior colleague's pass.

    Tested — proven on real reports: the mechanical checks and AI audits run and catch real issues, but the firm-specific rulebook isn't loaded yet.

    Not yet tested — it runs, but treat the output as an experiment, and tell Sureal what you see.

  3. Upload. Choose the report (.docx), select the scheme, credit and stage, and confirm the building name. (About a minute.)
  4. Wait — 5 to 20 minutes depending on document size. The status page shows each phase live; you can close the tab and come back.
  5. Download. The file keeps its original name — save it over your working copy, or next to it. You're done when the document opens in Word with comments in the margin.

Reading the output — one minute to learn

Every comment the system writes has the same four parts:

Sureal Report Reviewer
[TERM.2] LOW — Terminology

The document uses “dismountable”; the BREEAM term is “demountable”.

Action Required: replace “dismountable” with “demountable” throughout section 3.2.

Source: rule TERM.2 · calibrated

Rule + severity → what's wrong, in one line → Action Required tells you exactly what to change → Source names the rule that produced it.

SeverityWhat to do
CRITICALFix before the report goes anywhere. Rare by design — more than a couple means the document has a real problem.
HIGHFix before submission — a likely assessor finding.
MEDIUMFix unless you have a documented reason not to.
LOWPolish — seconds each, fix in the same pass.

The review is honest about itself. An uncalibrated credit says so in its output. If one of the audit passes couldn't run, the result says “complete — N of M audits unavailable” with the reason. What you see is exactly what was checked — and what wasn't.

Reply to the comments — this is where the teaching happens

Your replies in Word are how the system learns. Three replies carry meaning:

Agreeagreed, will fix

Confirms the rule is earning its place.

Disagree + whydisagree — this is in annex 3

The most valuable reply you can write. Recurring disagreement flags the rule for expert review and retunes it.

Suppressstop flagging this

Tells the system this check isn't wanted; enough of these and the rule is retired.

Silence counts weakly as agreement — a wrong comment left unanswered stays wrong next month. Two lines of reply fixes next month's reviews, not just this document.

The one golden rule: keep working in the reviewed file. Your replies only exist in the document that holds them — copy the text into a fresh file and the teaching dies with the old one.

2 · Providing feedback to the AI

Your replies only teach the system if they reach it. The channel is one shared folder — no forms, no mails, no exports.

How it works

Your admin has connected the app to a shared calibration folder in your organisation's OneDrive/SharePoint. Everything dropped there is collected once a month, turned into verdicts, reviewed rule by rule by a human expert, and published to the whole team as an update. Nothing changes the AI automatically — a person approves every rule. And your own feedback comes back as behaviour: the comment you corrected this month stops appearing next month.

One-time check — is the folder connected? (30 seconds)

Open File Explorer → your organisation's OneDrive/SharePoint area → you should see the Calibration folder with a green sync check. If it isn't there, or its files show a cloud icon instead of a check, ask your admin — there is nothing for you to configure.

Handing over a document — the entire “upload”

  1. Finish your replies in Word, save, and close the file.
  2. Drop a copy into the calibration folder. That's it — the folder is the upload.
  3. Leave it alone: no renaming, no moving it out, one copy per report per month. The monthly round pairs each file against the system's own records — renaming breaks the pairing. You're done when the file shows the green sync check.

What happens with it

At month-end, the system turns the month's replies and disputed comments into a short verdict workbook; your experts mark agree / disagree / suppress — a few minutes, once a month. The admin then approves or rejects every proposal individually, and the result reaches everyone through the ordinary update banner. Your two-line reply in March is a better review in April.

Also feeding this folder: candidates files from teaching a new credit its rules — see §8.

3 · If a report fails

Runs almost never fail — but when one does, you do exactly one thing: send a screenshot. There is nothing to troubleshoot on your side, ever.

First — has it actually failed?

Still working — do nothing

Slow is normal

5–20 minutes is a normal run, and the status page shows a live heartbeat while phases complete. As long as phases keep ticking, walk away and come back — a slow run is not a failed run.

Failed — send the screenshot

The page tells you

A failed run shows a red error panel on the status page, or says “possibly stalled” and stays that way after a refresh. That page is the error log — which is exactly why the fix is a screenshot.

The three steps

  1. Screenshot the status page — the whole browser window, so the error panel and the phase list are both visible. Press Win + Shift + S, drag across the window, done. That one image tells Sureal everything: which phase, which error, when.
  2. Email it to Ruben with one line of context — which credit, and roughly when you started the run.
    ✉ Mail the screenshot → ruben.geudens@sureal.be
  3. That's it. Leave the tab open if you can, and carry on with other work — you don't need to retry, refresh, or reinstall anything. You're done when the mail is sent. The fix happens on Sureal's side.

Why runs fail — the two usual suspects

💳

The AI usage budget ran out. Reviews run on metered AI credits (a usage budget — nothing to do with BREEAM credits). When the budget is exhausted, runs fail until it's topped up — a same-day fix on Sureal's side, and the most common cause by far.

⛈

The AI provider is overloaded or down. Rare and always temporary. Nothing to fix anywhere — the run simply works again later. Your screenshot still helps: it tells Sureal whether anything else is going on.

Neither cause is your document, and neither is your machine. If a run fails for any other reason, the screenshot is precisely what lets Sureal find and fix it — often before you've finished your coffee.

Your document is always safe. The system works on a copy of your upload — a failed run never touches or damages your file. Re-running the same report after Ruben gives the all-clear is always safe.

4 · The big picture

We have entered the era where software improves itself. This is what that looks like for BREEAM review.

Traditional software is finished the day it ships, and ages from that moment. This system is the opposite: it is an agentic micro-engine — a growing body of firm-owned knowledge (calibrated rules, reviewer verdicts, regulation packs, coverage ledgers) that every review adds to, and that AI agents read, apply, and extend. The software your team uses next quarter will be measurably better than today's — not because a vendor shipped an update, but because your own reviewed reports taught it. Improvement is the product's default state; humans approve every step of it.

The concrete problem it solves today: Sureal reviews BREEAM credit reports with a four-pairs-of-eyes principle — every draft is read, in full, by multiple senior reviewers before it reaches a client. That produces excellent reviews, and consumes senior hours on every report, on checks that repeat from document to document: terminology, consistency, completeness, the firm's hard-won rules about what assessors accept.

This system captures those repeating checks — distilled from hundreds of historical reviewer comments into a calibrated, firm-owned rulebook — and applies all of them, every time, provably, writing its findings as ordinary Word comments into the document itself. The senior eyes then do what only senior eyes can: judge, decide, and sign.

The product is not any single credit review. The product is the infrastructure plus the rulebook — a system Sureal's team extends themselves (new credits, new rules, new schemes) and that compounds: every reviewed report can teach the next one.

5 · The current solution — and why it's the right one

A reviewed document goes through a pipeline of thirteen steps. The principle: deterministic code where determinism belongs, AI where judgment belongs, and a ledger proving nothing was skipped — with failures reported just as loudly as findings: if an audit cannot be delivered, the review says so on its face instead of pretending completeness. Trust is symmetric.

Extracttext, tables, figuresCODE
Mechanical checksformatting · names · scheme matchCODE
Audit wavenumbers · quality · visuals · annexes — in parallelAI
Rule sweepevery calibrated rule: finding or checked-cleanAI
Consolidatemerge · dedupe · prioritiseAI
Word commentsanchored in the documentCODE
Verify + ledgercoverage proven per ruleCODE

The step that matters most is the rule sweep: the system must return a verdict on every rule in the firm's rulebook — a finding anchored to the exact sentence, or an explicit "checked, clean" with a reason. The count is enforced by code. Coverage is not hoped for; it is a file (rule_coverage.json) delivered next to every review.

Why not just paste the report into a chatbot?

Because a chat gives you a sample; this gives you a guarantee. Five differences, each testable: (1) a chat produces different findings every run — this checks all rules, every run, provably, and measures its own run-to-run consistency (see the box below). (2) A chat knows BREEAM; it doesn't know Sureal — the rulebook is the firm's own judgment, found in no model's training data. When we measured it, a generic review deployed zero of the firm's calibrated rules; this system deploys all of them. (3) A chat outputs text to copy-paste; this writes anchored Word comments into the client's own file. (4) A chat forgets each session; here, every reviewer reply becomes candidate training for next month's rulebook. (5) A chat changes behaviour silently when the vendor updates; this system is versioned — behaviour changes arrive as deliberate, tested releases you can diff. Full measured evidence: Addendum A.

And a chat “project” with the rulebook attached?

A fair upgrade to try — load the rulebook into a persistent project (Claude Projects and similar features), and every conversation starts with the firm's knowledge already in context. It is where our own first prototype started, and it genuinely narrows difference (2). But it leaves the other four untouched — and it only half-solves the one it addresses. Rules sitting in the context window are material the model may draw on, not checks it must perform: nothing enforces a verdict on every rule, nothing writes a coverage ledger, and no two runs apply the same subset. You have built a better-informed sample — still not a guarantee. Delivery is still copy-paste (3); reviewer replies still evaporate when the tab closes (4); and the attached knowledge file now evolves by hand-edit — unversioned, unapproved, unmeasured — which is silent drift (5) moved in-house rather than eliminated. The difference between a project and this system is the difference between handing an intern the manual and running an audit: the same information is in the room, with an entirely different guarantee about what was done with it.

Measured, August 2026. We ran 14 real client reports — every calibrated credit plus two uncalibrated ones — through the system twice, end to end. All 28 runs completed with every audit delivered. 89% of individual rule verdicts were identical across the two runs — and the system names each rule that wavered, feeding the next calibration round. A chat can't tell you its own consistency; this system measures it on every release.

Coming next (v1.3): we identified the single component responsible for most of the remaining variance — the AI-based consolidation step — and are replacing it with accountable code that keeps an auditable ledger of every finding. Measured target: pushing verdict stability beyond 90%, with the before/after numbers published in the release notes. Improvements arrive as versioned, measured releases — never as silent drift.

6 · How to install

You need: a Windows 10/11 PC (no admin rights required), the personal installer Sureal sends you (it is personal to your organisation — don't forward it), and the API key Sureal provides through a separate channel.

  1. Save install-win.zip from Sureal's most recent mail into your Downloads folder. No need to extract it — the next step does that for you.
  2. Open PowerShell (normal, not "as administrator").
  3. Paste this line and press Enter — it finds the installer in Downloads, extracts it if needed, and starts it: 
    cd $HOME\Downloads; $z = Get-ChildItem install-win*.zip -ErrorAction SilentlyContinue | Sort-Object LastWriteTime -Descending | Select-Object -First 1; if ($z) { Expand-Archive $z.FullName -DestinationPath . -Force }; $s = Get-ChildItem -Recurse -Filter install-win.ps1 -ErrorAction SilentlyContinue | Sort-Object LastWriteTime -Descending | Select-Object -First 1; if (-not $s) { Write-Host "[ERROR] install-win.zip not found - save the file from Sureal's mail into Downloads first" -ForegroundColor Red } else { powershell -ExecutionPolicy Bypass -File $s.FullName }
    If it prints a red install-win.zip not found, the file isn't in Downloads yet — save it from the mail and paste the same line again. Old installer copies expire; always use the one from the most recent mail.
  4. Follow the prompts. The installer finds what it needs on your machine (fetching portable tools where necessary), downloads the software, asks once for the API key (type it yourself — keys are never sent in the same mail as the installer), runs a self-test, and opens the app in your browser.
  5. From now on, open the app via the Sureal Report Reviewer icon the installer placed on your desktop — it starts the app if it isn't running and opens it in your browser (at http://127.0.0.1:8000). Everything runs entirely on your own machine; documents never leave it except for the AI review calls.

If it stops on a network error, ask Sureal for the offline dependency bundle and re-run with that folder beside the installer. If it says a package doesn't support your Python version, send Sureal that exact line — it is not a network or certificate problem.

Updating

When a new version exists, a banner appears in the app: "Version X available." Open the Update page and click once. The updater is transactional — it checks nothing is running, backs everything up, applies the update, re-runs the full self-test, and rolls back automatically if anything fails — and it has been proven in the field, not just in theory. Your local data is never touched.

7 · How to generate a review

  1. Open the app → Upload. Choose the report (.docx), select the scheme (NC2016 / RFO2015 / V6 / V7), the credit, the stage, and confirm the building name.
  2. Wait — typically 5 to 20 minutes depending on the size of the document. The status page shows each phase as it completes, the elapsed time, and a live activity heartbeat; if progress genuinely stops, it says "possibly stalled" instead of spinning forever.
  3. Download. The file keeps its original name — save it over your working copy or alongside it.
  4. Open it in Word. The review is there as ordinary comments, each anchored to the exact sentence it concerns, each labelled with its source rule and severity.
  5. Reply in Word to any comment you disagree with — a short "disagree, this is present in annex 3" or "stop flagging this" is enough. This is not politeness; it is how the system learns (§9). Agreeing silently is fine; disagreeing silently wastes the signal.

Honest completion. A run reports exactly what it delivered. If one of the audit passes could not be produced, the result says "complete — N of M audits unavailable" with the reason, and minor output-shape issues are attached as quality notes rather than hidden. You always know what was checked — and what wasn't.

Reading a comment

Every AI comment follows the same anatomy: [RULE.ID] SEVERITY — CATEGORY, a one-line issue, an Action Required telling you exactly what to change, and a Source line naming the rule that produced it. The severities mean:

LabelWhat it meansWhat to do
CRITICALCompliance-blocking: mandatory BREEAM evidence is missing or a core claim is unsupported. An assessor would likely reject this as it stands.Fix before the report goes anywhere. Rare by design — if you see more than a couple, something is genuinely wrong with the document.
HIGHA likely assessor finding: evidence gaps, contradictions between sections, unsubstantiated claims.Fix before submission.
MEDIUMWeakens the evidence or the document's consistency: vague commitments, template text, inconsistent KPIs, unclear scope.Fix unless you have a documented reason not to.
LOWPolish: terminology (e.g. BREEAM's "demountable"), British English, captions, formatting.Fix in the same pass; costs seconds each.

Replying — how the system hears you

Your replies in Word are read during calibration, and three kinds of reply carry meaning. Agree ("agreed", "will fix") — confirms the rule is earning its place. Disagree with a reason ("disagree — this is present in annex 3") — the most valuable reply you can write; recurring disagreement flags the rule for review and retunes it. Suppress ("stop making this comment") — tells the system this check isn't wanted; enough of these and the rule is retired. Silence counts weakly as agreement, so when a comment is wrong, two lines of reply is how you fix next month's reviews — not just this document.

The coverage ledger. Next to each review the system writes rule_coverage.json: which rules produced findings, which were checked and found clean. Nothing is sampled; everything is swept. You can show this file to a client or an assessor as evidence of review rigour.

If the document states a different BREEAM version than the scheme you selected, the review will flag it (SCH.1). That flag is usually right — check the project's actual registration before dismissing it.

8 · How to improve a credit module

Each credit (Mat 06, Tra 05, …) has its own rule pack. Packs start as scaffolds — the pipeline runs, mechanical checks work, but the credit-specific rulebook is empty.

Testing vs calibrating. Any report can test a credit today: upload one document — no reviewer comments needed — and the mechanical checks and the audit wave run immediately, with the rulebook layer reporting itself as uncalibrated. Calibrating — teaching the credit the firm's own rules — is what needs the reviewed history below.

What you feed itMinimum for a calibrated pack
Fully reviewed historical reports (.docx with the reviewers' comments still in them), same credit & stage8–10 documents. The reference-standard pack was calibrated on 8. Below that, the pack still works but is flagged low-confidence and its findings deserve extra scepticism.
Comment densityA useful document carries ≥ 6 substantive reviewer comments. Cover pages and sign-offs teach nothing.
  1. Collect the reviewed DOCX files. Do not rename anything to *_ORIGINAL.docx — that suffix is reserved by the system.
  2. App → Expert Rules → select the credit and stage → upload the documents.
  3. The system extracts every reviewer comment, clusters recurring concerns into candidate rules, and applies safety gates: a candidate needs a correct and an incorrect example, and must appear in at least two documents. Singletons are parked, not published.
  4. Candidates go to a staging file — never directly into the live rulebook. Drop the candidates file into the calibration folder (§9). Nothing takes effect until a human at Sureal has approved each rule individually.
  5. Approved rules arrive in a future update, and from then on every review of that credit applies them — with the coverage ledger proving it.

9 · The monthly calibration

Once a month, the system learns from the month's real work. Two signals feed it: the replies reviewers wrote on AI comments (§7 step 5), and new reviewed documents (§8). The collection point is the shared calibration folder on SharePoint/OneDrive that Sureal sets up with your team — keep it set to "Always keep on this device". The routine:

  1. Reviewers: keep working in the reviewed files, and drop the month's commented reports — plus any candidates files from §8 — into the calibration folder whenever convenient, end of month at the latest. That folder is the hand-over; no mails, no forms.
  2. Experts: the system turns the month's replies and disputed comments into a verdict workbook (Excel) — one row per disputed comment, mark agree / disagree / suppress. A few minutes, once a month, and it is the highest-leverage teaching your seniors can do.
  3. Admin (Sureal): every candidate rule and every verdict goes through an interactive approve/reject session — rule by rule, validated, version-stamped. Nothing reaches the live rulebook automatically. Accepted changes are published as a release.
  4. Everyone: the update banner appears; one click on the Update page and the improved rulebook is live for the whole team at once.

⚠ Pitfalls — each of these was learned the hard way

  • Never edit the rule database files by hand. A hand-calibrated ruleset was once overwritten by a well-intentioned bulk operation and survived only because of version control. All changes go through the staged approve flow, which validates before every write.
  • Keep working in the reviewed file. Your replies to the AI's comments are only visible to the system in the file that contains them. If you copy text into a fresh document, the learning signal dies with the old file.
  • Don't rename or move files out of the calibration folder. The monthly round pairs each file against the system's own records; renaming or relocating breaks the pairing. Let files live there, synced and hydrated.
  • One report, one upload per round. Uploading the same document twice inflates rule frequencies and can push weak rules over the acceptance threshold.
  • Resolve scheme flags, don't dismiss them. When the system raises SCH.1 (document says V6, review ran NC2016), confirm the project's actual registration first. This mismatch was found on multiple historical documents — it is not a false alarm by default.
  • A candidates file that never reaches the calibration folder does nothing. Until it is there and approved by Sureal, it's a proposal sitting in a folder. Drop it in.
  • Disagreement is data. The most valuable thing a reviewer can do for the system is reply "disagree — here's why" on a wrong comment. Suppressed annoyance teaches nothing; a two-line reply retrains the rulebook.

11 · This is a V1 — where it goes from here

What you are using today is the first rung of a ladder. The destination is not "AI instead of experts" — it is a steadily rising division of labour in which the human never leaves the loop; the loop moves up.

V1 — the tireless junior you are here
The system drafts the review; every calibrated rule is swept and proven. Experts still author the final judgment. Value: senior hours stop being spent on mechanical and rulebook checks. Reviewer time ≈ −40 %.
V2 — the reliable colleague
Months of reply-verdicts and monthly calibration have tuned the rulebook to the team. Drafts need visibly less correction; the coverage ledger ships with every client review as a rigour statement. Requires: sustained §9 discipline. Reviewer time ≈ −60 %.
V3 — validation-ready
The report review arrives practically flawless in Sureal's own voice — house terminology, house structure, house judgment — because the style itself is learned from accumulated verdicts. The expert's role shifts from author to approver: read, decide, sign. Requires: the evaluation harness proving per-rule precision, so "practically flawless" is a measured claim, not a feeling. Reviewer time ≈ −80 %.
V4 — the standard
New staff are trained by the system's rulebook rather than the reverse. The firm's expertise is an institutional asset — versioned, auditable, teachable — not tacit knowledge in a few senior heads.

Each rung is earned by data, not declared by software: V2 by calibration months, V3 by measured precision. The calculator above has a stage toggle — the business case for climbing is yours to inspect.

12 · The admin seat — governance and setup

Every install can capture: rules proposed from reviewed documents, and verdicts on the AI's comments. Exactly one install per organisation — the admin seat — reviews, approves, and publishes them. Nothing reaches any rulebook without that seat's human approve/reject, rule by rule; accepted changes reach the whole team as a versioned release through the ordinary update banner. On every other install the admin page simply does not exist — not hidden behind a login, absent by design. Two separate things make a seat the admin: a local flag (shows the page at all) and a write token (allows publishing). The flag without the token can review but never release.

One-time setup — step 1 · Activate the admin page

The flag is deliberately not settable from the web interface. On the admin's machine, open PowerShell (normal, not "as administrator") and paste:

cd "$env:LOCALAPPDATA\Sureal\breeam-pipeline"; & ".\.venv\Scripts\python.exe" -c "from calibration import admin; admin.set_admin(True); print('is_admin:', admin.is_admin())"

What you'll see: is_admin: True and nothing else. Reload the app — a Rules admin entry appears in the top bar. To deactivate, run the same line with False; the admin page then returns "not found" again, which is the correct state for every non-admin install.

Step 2 · The write token

On the GitHub account that owns the repository: Settings → Developer settings → Fine-grained tokens → Generate. Repository access: only the Sureal repository. Permissions: Contents = Read and write. Expiry: 1 year — put the expiry date in a calendar the day you mint it, because an expired token surfaces as a refused publish, not a warning. Name it after the seat.

The token is pasted once, into the "Write token" box on the Rules admin page, in the browser — nowhere else, ever. Three rules: (1) the token travels through no mail, no chat, no terminal; if it ever appears in one, treat it as compromised — revoke on GitHub, mint a new one. (2) After saving, the app shows only a short fingerprint; that fingerprint is the only way the token is ever displayed, and it is how you verify which token is stored. (3) This is the only read-write token in the fleet — every other install is read-only, which is precisely what makes this seat the only writer.

Step 3 · The calibration folder

The folder is the team's entire hand-over channel: reviewed documents and candidates files go in; the admin's queue fills itself from it.

  1. In the organisation's shared SharePoint/OneDrive library, create a folder named Calibration and sync it to the admin machine. Right-click it in Explorer → "Always keep on this device" — the sweep reads real files, not cloud placeholders.
  2. On the Rules admin page, point the app at that folder. The app drops a small marker file inside and creates its working subfolders (inbox, expert-review, processed, quarantine) — the marker is how every machine recognises the folder whatever its local path, so never delete it.
  3. Tell the team the one rule that matters: drop files into the folder and leave them alone — no renaming, no moving out. The monthly round pairs each file against the system's records; renaming breaks the pairing.

The routine

  1. Captured rules and feedback verdicts arrive via the calibration folder; "Check the folder now" (or the background sweep) ingests them into Waiting for review.
  2. When a round is due, export the Expert review sheet per credit. The returning sheet is read back through the same ingest — only its verdict and comment columns are ever applied; any other change to the sheet is surfaced as a proposal, never silently absorbed.
  3. Decide every queued item one at a time: Approve as proposed / Approve edited / Reject, with an optional "why" kept alongside the decision. Approving changes no rulebook by itself.
  4. Publish applies the whole approved set in one transaction — contract gate, version bump, release — and the team receives it through the ordinary update banner. Publish refuses, loudly and safely, while a review job is running, while nothing is approved, while the install is behind the latest release, or while program files have local edits.

Current version: on a Windows install, Publish can refuse with "local edits outside the data paths" naming four pack folders — a known false positive of the Windows file-link handling, not real damage. Until the fix ships: decide everything in the admin page as normal, then tell Sureal a release is ready; Sureal publishes it. This note disappears when the fix lands.

What it doesn't do (yet)

  • Uncalibrated credits run with an empty rulebook. The mechanical checks and the audit wave still run and still catch real issues — but there are no firm-specific rules to sweep until that credit has been calibrated (§8). The review says so, plainly.
  • V7 packs are scaffolds. They run, but they wait for real V7 review documents before they can learn anything worth applying.
  • Consistency is measured and improving — not absolute. 89% of rule verdicts identical across duplicate runs today, beyond 90% targeted in v1.3, with the numbers published each release. No review process, human or machine, is perfectly repeatable; this one is the only one that tells you its number.
  • It reviews; it doesn't author. The judgment, the signature, and the client relationship stay with your experts. That is the design, not a limitation.
