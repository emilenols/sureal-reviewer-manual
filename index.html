1 · The big picture

We have entered the era where software improves itself. This is what that looks like for BREEAM review.

Traditional software is finished the day it ships, and ages from that moment. This system is the opposite: it is an agentic micro-engine — a growing body of firm-owned knowledge (calibrated rules, reviewer verdicts, regulation packs, coverage ledgers) that every review adds to, and that AI agents read, apply, and extend. The software your team uses next quarter will be measurably better than today's — not because a vendor shipped an update, but because your own reviewed reports taught it. Improvement is the product's default state; humans approve every step of it.

The concrete problem it solves today: Sureal reviews BREEAM credit reports with a four-pairs-of-eyes principle — every draft is read, in full, by multiple senior reviewers before it reaches a client. That produces excellent reviews, and consumes senior hours on every report, on checks that repeat from document to document: terminology, consistency, completeness, the firm's hard-won rules about what assessors accept.

This system captures those repeating checks — distilled from hundreds of historical reviewer comments into a calibrated, firm-owned rulebook — and applies all of them, every time, provably, writing its findings as ordinary Word comments into the document itself. The senior eyes then do what only senior eyes can: judge, decide, and sign.

The product is not any single credit review. The product is the infrastructure plus the rulebook — a system Sureal's team extends themselves (new credits, new rules, new schemes) and that compounds: every reviewed report can teach the next one.

2 · The current solution — and why it's the right one

A reviewed document goes through a pipeline of thirteen steps. The principle: deterministic code where determinism belongs, AI where judgment belongs, and a ledger proving nothing was skipped — with failures reported just as loudly as findings: if an audit cannot be delivered, the review says so on its face instead of pretending completeness. Trust is symmetric.

Extracttext, tables, figuresCODE
Mechanical checksformatting · names · scheme matchCODE

The step that matters most is the rule sweep: the system must return a verdict on every rule in the firm's rulebook — a finding anchored to the exact sentence, or an explicit "checked, clean" with a reason. The count is enforced by code. Coverage is not hoped for; it is a file (rule_coverage.json) delivered next to every review.

Why not just paste the report into a chatbot?

Because a chat gives you a sample; this gives you a guarantee. Five differences, each testable: (1) a chat produces different findings every run — this checks all rules, every run, provably, and measures its own run-to-run consistency (see the box below). (2) A chat knows BREEAM; it doesn't know Sureal — the rulebook is the firm's own judgment, found in no model's training data. When we measured it, a generic review deployed zero of the firm's calibrated rules; this system deploys all of them. (3) A chat outputs text to copy-paste; this writes anchored Word comments into the client's own file. (4) A chat forgets each session; here, every reviewer reply becomes candidate training for next month's rulebook. (5) A chat changes behaviour silently when the vendor updates; this system is versioned — behaviour changes arrive as deliberate, tested releases you can diff. Full measured evidence: Addendum A.

And a chat “project” with the rulebook attached?

A fair upgrade to try — load the rulebook into a persistent project (Claude Projects and similar features), and every conversation starts with the firm's knowledge already in context. It is where our own first prototype started, and it genuinely narrows difference (2). But it leaves the other four untouched — and it only half-solves the one it addresses. Rules sitting in the context window are material the model may draw on, not checks it must perform: nothing enforces a verdict on every rule, nothing writes a coverage ledger, and no two runs apply the same subset. You have built a better-informed sample — still not a guarantee. Delivery is still copy-paste (3); reviewer replies still evaporate when the tab closes (4); and the attached knowledge file now evolves by hand-edit — unversioned, unapproved, unmeasured — which is silent drift (5) moved in-house rather than eliminated. The difference between a project and this system is the difference between handing an intern the manual and running an audit: the same information is in the room, with an entirely different guarantee about what was done with it.

Measured, August 2026. We ran 14 real client reports — every calibrated credit plus two uncalibrated ones — through the system twice, end to end. All 28 runs completed with every audit delivered. 89% of individual rule verdicts were identical across the two runs — and the system names each rule that wavered, feeding the next calibration round. A chat can't tell you its own consistency; this system measures it on every release.

Coming next (v1.3): we identified the single component responsible for most of the remaining variance — the AI-based consolidation step — and are replacing it with accountable code that keeps an auditable ledger of every finding. Measured target: pushing verdict stability beyond 90%, with the before/after numbers published in the release notes. Improvements arrive as versioned, measured releases — never as silent drift.

3 · How to install

You need: a Windows 10/11 PC (no admin rights required), the personal installer Sureal sends you (it is personal to your organisation — don't forward it), and the API key Sureal provides through a separate channel.

  1. Save install-win.zip from Sureal's most recent mail into your Downloads folder. No need to extract it — the next step does that for you.
  2. Open PowerShell (normal, not "as administrator") and paste the one line included in the delivery mail from Sureal.
  3. Follow the prompts. The installer finds what it needs on your machine (fetching portable tools where necessary), downloads the software, asks once for the API key (type it yourself — keys are never sent in the same mail as the installer), runs a self-test, and opens the app in your browser.
  4. Bookmark http://127.0.0.1:8000 — that's the app. It runs entirely on your own machine; documents never leave it except for the AI review calls.

If it stops on a network error, ask Sureal for the offline dependency bundle and re-run with that folder beside the installer. If it says a package doesn't support your Python version, send Sureal that exact line — it is not a network or certificate problem.

Updating

When a new version exists, a banner appears in the app: "Version X available." Open the Update page and click once. The updater is transactional — it checks nothing is running, backs everything up, applies the update, re-runs the full self-test, and rolls back automatically if anything fails — and it has been proven in the field, not just in theory. Your local data is never touched.

4 · How to generate a review

  1. Open the app → Upload. Choose the report (.docx), select the scheme (NC2016 / RFO2015 / V6 / V7), the credit, the stage, and confirm the building name.
  2. Wait — typically 5 to 20 minutes depending on the size of the document. The status page shows each phase as it completes, the elapsed time, and a live activity heartbeat; if progress genuinely stops, it says "possibly stalled" instead of spinning forever.
  3. Download. The file keeps its original name — save it over your working copy or alongside it.
  4. Open it in Word. The review is there as ordinary comments, each anchored to the exact sentence it concerns, each labelled with its source rule and severity.
  5. Reply in Word to any comment you disagree with — a short "disagree, this is present in annex 3" or "stop flagging this" is enough. This is not politeness; it is how the system learns (§6). Agreeing silently is fine; disagreeing silently wastes the signal.

Honest completion. A run reports exactly what it delivered. If one of the audit passes could not be produced, the result says "complete — N of M audits unavailable" with the reason, and minor output-shape issues are attached as quality notes rather than hidden. You always know what was checked — and what wasn't.

Reading a comment

Every AI comment follows the same anatomy: [RULE.ID] SEVERITY — CATEGORY, a one-line issue, an Action Required telling you exactly what to change, and a Source line naming the rule that produced it. The severities mean:

LabelWhat it meansWhat to do
CRITICALCompliance-blocking: mandatory BREEAM evidence is missing or a core claim is unsupported. An assessor would likely reject this as it stands.Fix before the report goes anywhere. Rare by design — if you see more than a couple, something is genuinely wrong with the document.
HIGHA likely assessor finding: evidence gaps, contradictions between sections, unsubstantiated claims.Fix before submission.
MEDIUMWeakens the evidence or the document's consistency: vague commitments, template text, inconsistent KPIs, unclear scope.Fix unless you have a documented reason not to.
LOWPolish: terminology (e.g. BREEAM's "demountable"), British English, captions, formatting.Fix in the same pass; costs seconds each.

Replying — how the system hears you

Your replies in Word are read during calibration, and three kinds of reply carry meaning. Agree ("agreed", "will fix") — confirms the rule is earning its place. Disagree with a reason ("disagree — this is present in annex 3") — the most valuable reply you can write; recurring disagreement flags the rule for review and retunes it. Suppress ("stop making this comment") — tells the system this check isn't wanted; enough of these and the rule is retired. Silence counts weakly as agreement, so when a comment is wrong, two lines of reply is how you fix next month's reviews — not just this document.

The coverage ledger. Next to each review the system writes rule_coverage.json: which rules produced findings, which were checked and found clean. Nothing is sampled; everything is swept. You can show this file to a client or an assessor as evidence of review rigour.

If the document states a different BREEAM version than the scheme you selected, the review will flag it (SCH.1). That flag is usually right — check the project's actual registration before dismissing it.

5 · How to improve a credit module

Each credit (Mat 06, Tra 05, …) has its own rule pack. Packs start as scaffolds — the pipeline runs, mechanical checks work, but the credit-specific rulebook is empty.

Testing vs calibrating. Any report can test a credit today: upload one document — no reviewer comments needed — and the mechanical checks and the audit wave run immediately, with the rulebook layer reporting itself as uncalibrated. Calibrating — teaching the credit the firm's own rules — is what needs the reviewed history below.

What you feed itMinimum for a calibrated pack
Fully reviewed historical reports (.docx with the reviewers' comments still in them), same credit & stage8–10 documents. The reference-standard pack was calibrated on 8. Below that, the pack still works but is flagged low-confidence and its findings deserve extra scepticism.
Comment densityA useful document carries ≥ 6 substantive reviewer comments. Cover pages and sign-offs teach nothing.
  1. Collect the reviewed DOCX files. Do not rename anything to *_ORIGINAL.docx — that suffix is reserved by the system.
  2. App → Expert Rules → select the credit and stage → upload the documents.
  3. The system extracts every reviewer comment, clusters recurring concerns into candidate rules, and applies safety gates: a candidate needs a correct and an incorrect example, and must appear in at least two documents. Singletons are parked, not published.
  4. Candidates go to a staging file — never directly into the live rulebook. Drop the candidates file into the calibration folder (§6). Nothing takes effect until a human at Sureal has approved each rule individually.
  5. Approved rules arrive in a future update, and from then on every review of that credit applies them — with the coverage ledger proving it.

6 · The monthly calibration

Once a month, the system learns from the month's real work. Two signals feed it: the replies reviewers wrote on AI comments (§4 step 5), and new reviewed documents (§5). The collection point is the shared calibration folder on SharePoint/OneDrive that Sureal sets up with your team — keep it set to "Always keep on this device". The routine:

  1. Reviewers: keep working in the reviewed files, and drop the month's commented reports — plus any candidates files from §5 — into the calibration folder whenever convenient, end of month at the latest. That folder is the hand-over; no mails, no forms.
  2. Experts: the system turns the month's replies and disputed comments into a verdict workbook (Excel) — one row per disputed comment, mark agree / disagree / suppress. A few minutes, once a month, and it is the highest-leverage teaching your seniors can do.
  3. Admin (Sureal): every candidate rule and every verdict goes through an interactive approve/reject session — rule by rule, validated, version-stamped. Nothing reaches the live rulebook automatically. Accepted changes are published as a release.
  4. Everyone: the update banner appears; one click on the Update page and the improved rulebook is live for the whole team at once.

⚠ Pitfalls — each of these was learned the hard way

  • Never edit the rule database files by hand. A hand-calibrated ruleset was once overwritten by a well-intentioned bulk operation and survived only because of version control. All changes go through the staged approve flow, which validates before every write.
  • Keep working in the reviewed file. Your replies to the AI's comments are only visible to the system in the file that contains them. If you copy text into a fresh document, the learning signal dies with the old file.
  • Don't rename or move files out of the calibration folder. The monthly round pairs each file against the system's own records; renaming or relocating breaks the pairing. Let files live there, synced and hydrated.
  • One report, one upload per round. Uploading the same document twice inflates rule frequencies and can push weak rules over the acceptance threshold.
  • Resolve scheme flags, don't dismiss them. When the system raises SCH.1 (document says V6, review ran NC2016), confirm the project's actual registration first. This mismatch was found on multiple historical documents — it is not a false alarm by default.
  • A candidates file that never reaches the calibration folder does nothing. Until it is there and approved by Sureal, it's a proposal sitting in a folder. Drop it in.
  • Disagreement is data. The most valuable thing a reviewer can do for the system is reply "disagree — here's why" on a wrong comment. Suppressed annoyance teaches nothing; a two-line reply retrains the rulebook.

8 · This is a V1 — where it goes from here

What you are using today is the first rung of a ladder. The destination is not "AI instead of experts" — it is a steadily rising division of labour in which the human never leaves the loop; the loop moves up.

V1 — the tireless junior you are here
The system drafts the review; every calibrated rule is swept and proven. Experts still author the final judgment. Value: senior hours stop being spent on mechanical and rulebook checks. Reviewer time ≈ −40 %.
V2 — the reliable colleague
Months of reply-verdicts and monthly calibration have tuned the rulebook to the team. Drafts need visibly less correction; the coverage ledger ships with every client review as a rigour statement. Requires: sustained §6 discipline. Reviewer time ≈ −60 %.
V3 — validation-ready
The report review arrives practically flawless in Sureal's own voice — house terminology, house structure, house judgment — because the style itself is learned from accumulated verdicts. The expert's role shifts from author to approver: read, decide, sign. Requires: the evaluation harness proving per-rule precision, so "practically flawless" is a measured claim, not a feeling. Reviewer time ≈ −80 %.
V4 — the standard
New staff are trained by the system's rulebook rather than the reverse. The firm's expertise is an institutional asset — versioned, auditable, teachable — not tacit knowledge in a few senior heads.

Each rung is earned by data, not declared by software: V2 by calibration months, V3 by measured precision. The calculator above has a stage toggle — the business case for climbing is yours to inspect.

Beyond the ladder — the iteration engine

The ladder describes the review getting better. The bigger opportunity is the rest of the value chain. Look at the life of a credit report today:

Evidence & figuresmaps · screenshots · annotationsHUMAN

Correctionreviewer + AI commentsHUMAN + AI

Only one step is automated so far. Every [HUMAN] box is a candidate for the same treatment — and because the system's knowledge lives in a repository agents can read, the system can propose these expansions itself. A concrete example: for transport credits, a person today takes map screenshots and hand-annotates transit stops, walking distances and amenities. An agent that has read this project can notice that, propose it, and build a prototype that generates those figures from a project address — evaluated against the figures in historical reports, approved by a human, and only then added to the pipeline. Analyse → propose → prototype → measure → approve → graduate: the same gated loop that governs the rulebook, applied to the software's own scope.

That is the story this project tells: not a tool that was built once, but a system that keeps finding its own next improvement — with Sureal's experts holding the approval pen at every step.

What it doesn't do (yet)

  • Uncalibrated credits run with an empty rulebook. The mechanical checks and the audit wave still run and still catch real issues — but there are no firm-specific rules to sweep until that credit has been calibrated (§5). The review says so, plainly.
  • V7 packs are scaffolds. They run, but they wait for real V7 review documents before they can learn anything worth applying.
  • Consistency is measured and improving — not absolute. 89% of rule verdicts identical across duplicate runs today, beyond 90% targeted in v1.3, with the numbers published each release. No review process, human or machine, is perfectly repeatable; this one is the only one that tells you its number.
  • It reviews; it doesn't author. The judgment, the signature, and the client relationship stay with your experts. That is the design, not a limitation.
